# Дорожный роутер (OSRM) — зоны прибытия по улицам

## Зачем

Зона прибытия части до сих пор считалась геодезическим буфером: круг радиусом
3,5 км ≈ десять минут хода. Круг не знает ни реки Есиль, ни железной дороги,
ни закрытых кварталов — он рисует покрытие там, где машина не проедет. На
карте это неточность; в выводе «этот район прикрыт» — ошибка, на которой
основывают решения о размещении частей.

С поднятым роутером те же ручки (`/infra/coverage`, `/infra/blind-zones`,
`/infra/stats`) считают достижимость по дорожному графу OSM.

## Что важно знать до включения

**OSRM считает по свободному потоку.** Ни заторов, ни гололёда, ни разъезда
во дворе. На данных Астаны это даёт зоны *шире* прежнего круга: на локальном
стенде «слепых» зданий стало 15 вместо 690. Это не значит, что город внезапно
прикрыт, — это значит, что расчёт по свободному потоку оптимистичен так же,
как круг был пессимистичен.

Поэтому:

- ответы помечены `traffic_unaccounted: true`, а карта подписывает слой
  «по дорогам · без учёта заторов»;
- есть множитель `FW_ROUTING_TIME_FACTOR` (по умолчанию `1.0` — никакой
  скрытой правки данных);
- множитель не выдумывается, а калибруется по своим же выездам:
  `GET /infra/routing/calibration` сравнивает фактическое время хода
  (`выезд → прибытие` из хронологии закрытых выездов) с расчётным по тому же
  маршруту и предлагает медиану отношения. Меньше десяти выездов —
  `enough_data: false`, и предлагать по ним коэффициент для целого города
  нельзя.

Применяет множитель человек, вписав его в `.env`. Автоподстановки нет
намеренно: коэффициент меняет картину покрытия города.

## Установка

```bash
./ops/osrm/prepare.sh                      # ~210 МБ выгрузки, 10–15 минут
docker compose --profile routing up -d osrm
echo 'FW_ROUTING_URL=http://osrm:5000' >> .env
docker compose up -d api                   # restart не перечитывает env

# пересчёт зон (admin) — тяжёлая операция, делается явно и редко
curl -X POST localhost:8001/infra/coverage/rebuild -H "Authorization: Bearer <token>"
```

Проверка: `GET /infra/routing/health` → `{"configured": true, "ok": true}`.

Без `FW_ROUTING_URL` всё работает как раньше: буфер и `approximate: true`.
Профиль `routing` в compose тоже не поднимается по умолчанию — установке без
подготовленного графа он не нужен.

## Как считается изохрона

OSRM не умеет изохроны нативно, зато умеет матрицу времён (`/table`). Вокруг
части раскладывается сетка точек с шагом `FW_ROUTING_GRID_STEP_M` (400 м),
одним запросом берутся времена хода до каждой, остаются уложившиеся в
норматив. Зона — объединение кружков вокруг оставшихся точек, а не выпуклая
оболочка: оболочка «залила» бы дыры, и закрытый квартал внутри зоны выглядел
бы прикрытым.

Результат лежит в таблице `station_isochrones` (миграция 0022). Матрица на
тысячу точек считается секунды, карту открывают десятки раз в день, а сеть
дорог меняется раз в месяц — поэтому расчёт отделён от чтения.

## Данные

`ops/osrm/data/` в git не хранится (см. `.gitignore`): выгрузка и граф — это
около 1 ГБ, которые воспроизводятся скриптом за десять минут.

## Чего здесь пока нет

**Приоритетного проезда.** Пожарная машина с проблесковыми маячками едет по
выделенным полосам и на красный, а профиль `car.lua` считает её обычным
автомобилем. Своего профиля мало — нужна разметка: в OSM Астаны сейчас 45
сегментов с тегами `busway`/`lanes:bus`, то есть выделенные полосы размечены
частично. Пока это так, «маршрут по выделенным полосам» дал бы преимущество
на нескольких проспектах и молчание на остальном городе — обещание, которое
данные не покрывают.
