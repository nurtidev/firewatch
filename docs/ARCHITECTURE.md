# FireWatch — архитектура

> Платформа пожарной безопасности для ДЧС РК и акиматов. Пилот — Астана.
> Прод: https://www.firewatch.kz (Railway). Документ описывает **текущий код** (сентябрь 2026).
> Правила разработки, дизайн-система, тестовые учётки и деплой — в [CLAUDE.md](../CLAUDE.md)
> и скилле `deploy-railway`; здесь они не дублируются.

---

## 1. Общая схема

```
              Браузер / планшет РТП / телефон инспектора (PWA, sw.js, офлайн-очереди)
                                   │
                         ┌─────────▼─────────┐
                         │  web  (Next.js 15) │  React 19, Tailwind v4, MapLibre GL, three.js
                         └─────────┬─────────┘
                                   │ REST + JWT (Bearer; ?token= для <img>/<iframe>)
                         ┌─────────▼─────────┐        ┌──────────────────────────┐
                         │  api  (FastAPI)    │───────►│ Claude API (Anthropic)   │
                         │  SQLAlchemy+Alembic│        │ извлечение ПТП, ИИ-чат   │
                         └──┬──────────┬──────┘        └──────────────────────────┘
               HTTP (private)│          │ SQL (psycopg, 2 пула: запросы + аудит)
              ┌──────────────▼──┐   ┌───▼───────────────────────┐
              │ ml (FastAPI)    │   │ PostgreSQL 16 + PostGIS 3.4│
              │ XGBoost + SHAP  │   │ здания, районы, части,     │
              └─────────────────┘   │ выезды, ПТП, аудит (WORM)  │
                                    └───────────────────────────┘
   Опционально (выключено по умолчанию):
     OSRM (FW_ROUTING_URL)            — зоны прибытия по дорогам вместо буфера
     Телематика Wialon (FW_TELEMATICS_*) — позиции техники; сейчас provider=none
   Внешние при импорте: Overpass API (OSM-здания, границы районов).
```

### Сервисы

| Сервис | Стек | Где | Назначение |
|---|---|---|---|
| `web` | Next.js 15 (App Router, standalone `node server.js`), React 19, Tailwind v4 (CSS-first, без shadcn), MapLibre GL 4.7, three.js, lucide-react | Railway, :3001 локально | UI обоих треков, лендинги `/`, `/gov`, `/business`, PWA |
| `api` | FastAPI, SQLAlchemy (сырой SQL через `text()`), Alembic, psycopg 3, anthropic SDK, sqlglot | Railway, :8001 | Auth/RBAC, все доменные роутеры, аудит, кэш агрегатов |
| `ml` | FastAPI, XGBoost + Platt-калибровка, TreeSHAP | Railway, только private network, :8002 | Инференс оценки уязвимости и SHAP-вкладов, метрики модели |
| `db` | `postgis/postgis:16-3.4` | Railway (volume), локально :5432 | Единственное хранилище |
| `osrm` | `osrm-backend`, граф Казахстана | **только локально**, compose-профиль `routing` | Изохроны по улицам; на Railway не развёрнут |
| cron `compute_risk` | образ api, `api/railway.cron.json` (`0 2 * * *` = 07:00 Астаны) | конфиг в репо; отдельного сервиса в карте прода `deploy-railway` нет | Пересчёт `risk_scores` через ml |

Сборка всех сервисов — Dockerfile. `ml` обучает модель **на этапе `docker build`**
(`python -m train.train`), гейт качества ROC-AUC ≥ 0.78 валит сборку. `api` самомигрирующийся:
preDeploy = `alembic upgrade head` → `seed_districts` → идемпотентные сиды структурных ПТП
(`seed_hayvill`, `seed_extra_objects`). Загрузки (сканы ПТП, фото) — volume `api-volume` в `/app/uploads`.

## 2. Модель данных

Схема ведётся Alembic-миграциями `api/migrations/versions/0001…0026`. `0001_baseline` исполняет
замороженный `api/app/schema.sql`; дальше — только явный DDL. Геоиндексы GiST на всех `geom`.

| Таблица | Миграция | Что хранит |
|---|---|---|
| `buildings` | 0001, 0003, 0016 | OSM-здания: geom, адрес, тип, год, этажность, район; признаки функциональной пожарной опасности (массовое пребывание, категория А–Д, газ); `search_norm`/`alias` для поиска без казахской диакритики |
| `risk_scores` | 0001 | score 0–100, `model_version`, `explanation` JSONB (SHAP-вклады) — отдельной таблицы объяснений нет |
| `incidents` | 0001 | история пожаров (пока демо) |
| `operational_cards`, `card_revisions` | 0001, 0013, 0018, 0025 | карточки ПТП: файл, извлечённый JSON, статус, район; версии и согласование, индекс по `building_id` |
| `prescriptions`, `remediations` | 0001, 0009, 0011 | предписания (из извлечения → `pending` → approve/reject), заявки владельцев об устранении |
| `inspectors`, `inspection_visits` | 0001, 0004, 0006, 0013 | реестр инспекторов (связь с `users`), визиты: нарушения с кодом нормы и сроком, тип проверки, фото |
| `field_reports` | 0010, 0014 | полевые донесения о препятствиях (проезд, гидрант, выход), `client_id` для идемпотентности офлайн-очереди |
| `users` | 0001, 0002, 0007, 0015, 0017, 0026 | роль, район, `station_id` (только у responder — инвариант в БД), `sessions_revoked_at`, `is_active` |
| `owner_buildings` | 0011 | привязка владельцев объектов к зданиям (портал) |
| `fire_stations`, `station_vehicles`, `hydrants` | 0001, 0008, 0017 | части и их техника; гидранты с давлением, диаметром, типом, статусом |
| `callouts`, `callout_vehicles`, `callout_resources` | 0012, 0017 | боевые выезды: хронология (сообщение → выезд → прибытие → ствол → локализация → ликвидация), наряд, расход средств |
| `deployment_positions`, `deployment_late_removals` | 0019–0021, 0024 | расстановка сил: на местности (geom) и на поэтажном плане (этаж, план-координаты, направление); клиентский id и время жеста для офлайна; досинхронизация после закрытия |
| `station_isochrones` | 0022 | сохранённые изохроны частей по дорогам (OSRM) |
| `districts` | 0023 | полигоны районов Астаны из OSM (ODbL), сид `seed_districts` |
| `audit_log` | 0002, 0005 | журнал входов, изменений и отказов; триггер запрещает UPDATE/DELETE (WORM) |

Чат-сессии в БД не хранятся (ИИ-аналитик без состояния); маршруты инспекций не материализуются —
считаются на лету.

## 3. Роли, треки, скоупинг

Роли: `inspector | supervisor | leadership | admin | owner | dispatcher | responder | akimat`
(`web/src/lib/auth.tsx`). Навигация и доступ страниц — `web/src/lib/nav.ts`:

| Трек | Раздел | Страницы |
|---|---|---|
| «Пожарные» | Реагирование | `/dispatch` (Пульт ЦОУ), `/callout` (+ `/callout/archive`, печатный `/callout/report`), `/cards`, `/forces`, `/vehicles` |
| «Пожарные» | Профилактика | `/routes`, `/control`, `/reports`, `/dashboard` («Сводка ДЧС»), `/map`, `/infra` |
| «Город» | — | `/city`, `/city/map`, `/city/priorities`, `/city/report` (печатный), `/chat` |
| «Система» | — | `/model`, `/audit`, `/users` |
| вне треков | — | `/portal` (owner), лендинги `/`, `/gov`, `/business`, `/login` |

Бэкенд (`api/app/access.py`):

- `FULL_ACCESS_ROLES = {leadership, admin}`; `CITYWIDE_ROLES = {leadership, admin, dispatcher, responder}` — весь город.
- inspector/supervisor — свой район; район пользователя читается из БД на каждый запрос, не из JWT.
  Район объекта считается по геометрии при записи (`districts.py::district_of`: `ST_Contains`, иначе
  ближайший полигон по geography — OSM-границы покрывают ~91% территории города).
- `CITY_READ_ROLES = {akimat}` — только агрегаты `/city/*` и здания (флаг `allow_city_read` в
  `enforce_building_scope`); ни ПДн, ни донесений, ни ПТП, ни чата. `api/tests/test_guards.py` обходит
  все маршруты OpenAPI и валится, если новый эндпоинт открыт акимату.
- responder привязан к части (`users.station_id`), назначается на «Пользователи».
- Сессии: JWT (TTL `FW_JWT_TTL_HOURS`), принудительный отзыв (`/auth/revoke` → `sessions_revoked_at`),
  отключение учётки (`is_active`).

## 4. Модули и ключевые потоки

### Оценка уязвимости (карта риска, `/map`, `/dashboard`, `/model`)
Слой называется **«объяснимая оценка уязвимости»** — не прогноз. Пайплайн:
`scripts/compute_risk.py` собирает признаки зданий → `ml POST /predict/batch` → `risk_scores` (score + SHAP).
Реальные из OSM только тип, этажность, год; остальные признаки **детерминированно синтезированы из
osm_id**, модель обучена на синтетике (`ml/artifacts/MODEL_CARD.md`: ROC-AUC 0.814, источник
`synthetic`). Контракт признаков готов к данным ДЧС (`train/dataset.py::from_incidents`).
Пороги severity (≥60/≥40/≥20) — единый источник `web/src/lib/risk.ts` и `RISK_BANDS` на бэкенде.

### План инспекций (`/routes`, `/control`)
`GET /routes/today`: здания района, ранжированные по риску × давности проверки (нормативный
интервал зависит от балла), обход — ближайший сосед. Визит: чек-лист, нарушения с кодом нормы и сроком,
фото. `/control` — ход выполнения для supervisor/leadership. Офлайн: `lib/offline.ts` (кэш маршрута
+ очередь визитов и донесений в localStorage, сжатие фото до 2 МБ).

### Полевые донесения (`/reports`)
Препятствия пожаротушению вне плана: точка + категория + фото, триаж
open → in_progress → resolved. Идемпотентность по `client_id`.

### Module 03 — оцифровка ПТП (`/cards`)
`POST /cards`: PDF/изображение → `extraction.py` → Claude (document block, `tool_choice` на
`EXTRACT_TOOL`) → структурные поля + предложенные предписания (статус `pending`, требуют решения
должностного лица). PDF > 20 МБ пересжимается PyMuPDF. Контакты маскируются и промптом, и бэкендом
(`_mask_contacts`, открыты только служебные линии). Редактор карточки с версиями и восстановлением
(`card_revisions`). Структурные карточки с 3D-моделью и схемами — из сидов; загруженный PDF даёт
«плоскую» карточку. Модель по умолчанию — `ANTHROPIC_MODEL=claude-sonnet-5`.

### Расчёт сил и средств (`/forces`)
`POST /forces/calc` — методика ДЧС (эталон «Есеп Евразия»): время свободного развития → площадь
пожара/тушения → требуемый расход → стволы, машины, личный состав, ранг пожара. Пресеты объектов
с Vл/Jтр. Связан с `/vehicles` (чем расчёт обеспечен фактически).

### Боевой модуль: выезд и расстановка (`/dispatch`, `/callout`)
1. Диспетчер ЦОУ ищет адрес (`/dispatch/search`, без диакритики) и регистрирует выезд, часть — ближайшая по умолчанию.
2. Караул получает **боевой пакет** (`/dispatch/{id}/pack`): ближайшие гидранты (800 м, `HYDRANT_RADIUS_M`),
   ПТП объекта, активные донесения о проезде, подсказка по силам.
3. РТП на планшете ведёт хронологию, наряд и расход, расстановку на местности и на поэтажном плане.
4. Закрытие → печатное донесение о пожаре (`/callout/report`), архив `/callout/archive`, «Расхождение с ПТП».

**Офлайн-расстановка** (`web/src/lib/deploymentQueue.ts` → `POST /dispatch/{id}/deployment/sync`):
не журнал жестов, а одно намерение на позицию (create+move схлопываются, create+delete выбрасывается),
пачкой при появлении связи; досинхронизация в закрытый выезд принимается (0024). Порядок деплоя при
изменении контракта — сначала api, потом web (422 в очереди окончательный).

### Покрытие и слепые зоны (`/infra`, `/city`)
Единый модуль `api/app/coverage.py` для `/infra/*` и `/city/*`. Без роутера — геодезический буфер
(3,5 км ≈ 10 мин) с `approximate: true`. С `FW_ROUTING_URL` — изохроны по матрице OSRM `/table`,
сохраняются в `station_isochrones`; `coverage_source = osrm | buffer | mixed`. Свободный поток без
заторов (`traffic_unaccounted: true`), множитель `FW_ROUTING_TIME_FACTOR` калибруется по выездам
(`/infra/routing/calibration`) и применяется вручную. При сбое пересчёта изохрона не удаляется, а
помечается устаревшей. Подробно — `ops/osrm/README.md`.

### Городской трек (`/city/*`)
Только агрегаты: сводка по районам, GeoJSON районов, приоритеты вложений (где нужны гидранты/части),
печатный отчёт. Ответы несут `demo_data`, `method`, `computed_at`; время прибытия — отдельно
`median_response_min` и `median_travel_min`. Атрибуция OSM обязательна.

### ИИ-аналитик (`/chat`, leadership/admin)
Text-to-SQL: Claude генерирует один SELECT по `SCHEMA_DOC`; sqlglot проверяет белый список таблиц
(без `users` и `operational_cards`) и запрещённые функции; выполнение в READ ONLY-транзакции с
тайм-аутом и лимитом строк; SQL возвращается как источник.

### Портал владельца (`/portal`)
Владелец видит одобренные предписания своих зданий и подаёт заявку об устранении (фото);
инспектор принимает или отклоняет.

### Аудит (`/audit`)
`AuditMiddleware` (чистый ASGI, запись в отдельном пуле через свой лимитер потоков) пишет каждый
мутирующий запрос и каждый 401/403; критичные ручки пишут собственную расширенную запись.
`audit_log` — append-only на уровне БД.

## 5. Нагрузка и отказоустойчивость (обновлено 2026-09-23)

- **Два пула БД** (`app/db.py`): запросы (`FW_DB_POOL_SIZE`, по умолчанию 5 + overflow) и аудит
  (`FW_DB_AUDIT_POOL_MAX`). Сессия закрывается до отправки ответа (`Depends(get_db, scope="function")`).
- **Тяжёлые чтения** (`heavy_read`) — `SET LOCAL statement_timeout` ниже тайм-аута пула.
- **503 вместо 500** с `Retry-After`: пул занят дольше `FW_DB_POOL_TIMEOUT_SEC`, либо запрос отменён
  (`QueryCanceled`) / база не приняла соединение. На мутациях 503 — только при `QueryCanceled`
  (иначе риск дубля записи). Web показывает объяснение сервера на городских страницах.
- **Кэш агрегатов чтения** (`app/cache.py`, в памяти процесса): `/city/summary`, контуры районов,
  `/city/priorities`, `/infra/coverage`, `/infra/blind-zones`. TTL `FW_READ_CACHE_TTL_SEC` (60 с),
  single-flight, stale-while-revalidate, предел ожидания холодного ключа, сброс при пересчёте зон и
  отметке гидранта. В DB-тестах отключён.
- Нагрузочный прогон: `ops/loadtest/city_burst.py` (всплески `/city/map`, зонд входа, `pg_stat_activity`).

### Офлайн (PWA)
`web/public/sw.js`: навигации — сеть, потом кэш (копия после 10 с); `_next/static` — кэш, потом сеть;
API — сеть, потом кэш, только GET из белого списка (боевой пакет, маршрут, ПТП), тайм-аут 4 с,
ответ из кэша помечен `X-FW-Cached` («снимок от …»). Кэш данных `fw-api` без версии (обновление SW
не стирает офлайн-пакеты). Мутации не кэшируются — доставка через очереди приложения.

## 6. Качество и эксплуатация

- CI (`.github/workflows/ci.yml`): api pytest на PostGIS (`firewatch_test`, миграции up → down → up),
  ml обучение + гейт + pytest, web `npm run build` + сверка severity-цветов с `globals.css`,
  `pip-audit`, `ruff` (класс ошибок).
- Fail-fast в проде (`FW_ENV=production`): api не стартует с дефолтными секретами/CORS; `ml /health`
  отдаёт 503 без загруженной модели.
- i18n интерфейса: RU/EN/KK (`web/src/lib/i18n/`).
- `ops/demo/` — сборка демо-ролика (озвучка + склейка), `ops/osrm/` — подготовка графа.
- Push в main не деплоит; деплой ручной per-service — см. `deploy-railway`.

## 7. Статус и что дальше

**Сделано (в коде и на проде):**
- Оба трека и системные экраны; RBAC по районам с реальными OSM-границами; akimat read-only с тестом-обходчиком.
- Боевой модуль: выезд, боевой пакет, хронология, наряд/расход, расстановка на местности и плане с офлайн-синхронизацией, донесение и архив.
- Module 03: извлечение ПТП через Claude, маскирование ПДн, редактор с версиями, согласование предписаний; структурные карточки с 3D для пилотных объектов.
- Расчёт сил и средств по методике, учёт техники частей.
- Инспекции с нарушениями/фото, полевые донесения, портал владельца — всё с офлайн-очередями.
- Покрытие по буферу и (опционально) по OSRM с калибровкой; городская сводка/отчёт/приоритеты.
- WORM-аудит, отзыв сессий и отключение учёток, устойчивость к перегрузке БД (пулы, 503, кэш).

**Открыто (зависит от данных и доступов ДЧС, а не от кода):**
- Модель обучена на синтетике, признаки частично синтезированы — нужна реальная история пожаров
  и паспортные данные объектов; до этого — только «оценка уязвимости», не прогноз.
- OSRM на Railway не развёрнут: прод считает покрытие буфером (`approximate`). Нужен сервис с
  графом и калибровка множителя по ≥10 реальным выездам.
- Телематика: адаптер Wialon готов, `FW_TELEMATICS_PROVIDER=none` до выдачи доступа.
- Cron `compute_risk`: конфиг есть, отдельного сервиса в карте прода нет — пересчёт запускается вручную.
- Гидранты и части — демо/импорт OSM; нужен фид водоканала и ДЧС (давление, исправность).
- Городские цифры помечены `demo_data` — мало частей и выездов в сидах.
- Нерешённые организационные вопросы: локализация данных ДЧС в РК (регион хостинга / on-prem,
  в т.ч. для Claude API с ПДн), источник зданий сверх OSM (2ГИС/госкадастр).
