## P0 — чинить первым

### 1. Боевой пакет занижает силы: ранг №2 вместо №3

РТП открывает «Открыть расчёт» из пакета вызова на ЖК «Аланда» и получает
**ранг №2, 2+1 ствола**. В привязанной к тому же вызову карточке ПТП лежит
расчёт по объекту: **ранг №3, 4+2 ствола, 7 отделений, Qобщ.тр = 19,47 л/с**.

Причина: у здания `building_type = "other"` (многофункциональное — гостиница +
медцентр + бомбоубежище), а `_TYPE_TO_PRESET` в `api/app/routers/dispatch.py:43-54`
про `"other"` не знает → `forces_hint = null` → кнопка ведёт в пустой калькулятор
с дефолтом «жилое». Диспетчер видит ту же проблему со своей стороны: ссылка на
`/forces` идёт **без единого параметра**, хотя этажность и тип система уже знает
(`web/src/components/CalloutPack.tsx:226`).

Цена ошибки: на 24-этажке с гостиницей внутри — недокомплект на один АЦ и три
ствола. Это не UX, это боевой расчёт.

**Фикс:** если у здания есть карточка с `force_calc` — брать рекомендацию оттуда;
`"other"` добавить в маппинг с безопасным (не заниженным) дефолтом; параметры
объекта передавать в `/forces` через query.

### 2. Этажность одного здания: 20 в пакете, 24 в карточке

`buildings.floors = 20` (реестр OSM) против «24 этажа» в оцифрованном ПТП
(`alanda.json`). РТП выбирает по этой цифре автолестницу.

**Фикс:** при наличии карточки ПТП — она источник истины для этажности; либо
синхронизировать реестр, либо в пакете показывать цифру из карточки.

### 3. Скоупинг по району дырявый — и это не одно место

Три независимых подтверждения:

- **Стартовый экран «План инспекций» у супервайзера Есильского района открывает
  маршрут инспектора Сарыаркинского** — 6 чужих адресов с нарушениями и
  просрочками, без единого клика. `GET /inspectors` и `GET /routes/today` не
  фильтруют по району (`api/app/routers/routes.py:85-93, 184-244`), хотя соседний
  `GET /routes/progress` в том же файле (`:361-380`) делает это правильно.
- **IDOR:** инспектор Сарыаркинского района запросил `GET /routes/today?inspector_id=2`
  и получил 200 с полным маршрутом инспектора Алматинского. Тот же незащищённый
  параметр принимает `POST /routes/visit` — то есть визит можно закрыть от чужого
  имени. Для акта, имеющего юридическую силу, это дефект целостности авторства.
- **`/cards` без district-скоупа** — инспектор видит карточки всего города.
  Комментарий в `api/app/routers/cards.py:40-41` объясняет это отсутствием FK,
  но колонка `building_id` в таблице есть и заполняется сидами. Комментарий устарел.

**Фикс:** единый слой скоупинга вместо поэндпоинтного; сверять `inspector_id` с
личностью вызывающего (нужен FK `users` ↔ `inspectors`, которого сейчас нет).

### 4. «Высокий риск» — два разных числа в одном продукте

| Экран | Что показывает | Порог |
|---|---|---|
| `/dashboard` | 72 по городу / 14 по району | `score > 70` (`overview.py:38-42`) |
| `/map`, `/chat`, `lib/risk.ts` | 302 по городу / 11+48 по району | 20 / 40 / 60 |

Подписи диапазонов на дашборде захардкожены («71–100», «36–70», «0–35») в
`web/src/app/dashboard/page.tsx:364-366`. CLAUDE.md требует синхронизировать
четыре места — дашборд в этот список не попал.

Руководство: «я не могу назвать на коллегии ни одно из этих чисел без оговорки».

**Фикс:** `overview.py` и подписи дашборда — на канонические пороги из `risk.ts`.
Дешевле всех остальных P0.

### 5. Уволенный сотрудник продолжает входить

Проверено последовательностью запросов: старый токен после `POST /auth/revoke` →
401 (работает), но `POST /auth/login` с тем же логином и паролем сразу после →
**200 и новый рабочий токен**. Ни `is_active`, ни сброса пароля, ни `DELETE` для
`users` в API нет.

Рядом: **завести сотрудника через продукт нельзя вообще** — `POST /auth/users`
жёстко ограничен `role="owner"`, внутренние роли только через правку
`api/scripts/seed_users.py` и `docker compose exec`. Плюс roster маршрутов живёт
в отдельной таблице `inspectors` без единого `POST` и без связи с `users`.

На вопрос аттестации «гарантированно ли уволенный не войдёт» честный ответ —
«нет».

### 6. ИИ-аналитик подменил город и не сказал

Вопрос «сколько объектов высокого риска в Алматы» (данных по другому городу нет).
Ответ: **«В Алматы 17 объектов высокого риска»**, SQL —
`WHERE b.district = 'Алматинский'`. Молча подставил район Астаны вместо города.

При этом на два других контрольных вопроса (причины пожаров 2019, список школ)
честно ответил «данных нет» — отказ работает, но не срабатывает на совпадении
по названию. Отдельно: `/chat` — единственный экран с цифрами риска **без плашки
о демо-данных**, и при этом самый цитируемый.

**Фикс:** в системный промпт — «база покрывает только Астану, при упоминании
другого города вернуть „данных нет“»; в тексте ответа называть отфильтрованное
значение («в районе „Алматинский“»); добавить `<DemoBanner />` на `/chat`.

## P1 — потеря работы пользователя и скорость

### 7. Поиск адреса требует точной казахской диакритики

Из 8 вариантов написания сработали 2. Не находит: `тауелсиздик 33` (та же улица
без казахских букв — `ә`, `і`), `сарайшик 7/1` (то же для `ы`, `қ`), опечатка в
номере дома, `Хайвилл` (народное имя ЖК). Поиск — `ILIKE` по токенам без
нормализации (`api/app/routers/dispatch.py:266-313`).

> **Важно про формулировку.** Названия улиц в РК **не переводятся** — только
> транслитерируются: «Тәуелсіздік» остаётся «Тәуелсіздік» и в русском тексте.
> Поэтому «независимости 33» — не тот кейс, который система обязана понимать, и
> искать перевод названий не нужно. Реальная проблема — **диакритика**:
> диспетчер печатает с русской раскладки, где нет `ә ғ қ ң ө ұ ү һ і`, и точное
> совпадение подстроки не срабатывает. Это и надо чинить.

**Фикс:** нормализация диакритики с обеих сторон сравнения (казахские буквы →
базовые кириллические) перед фильтрацией по токенам — например, отдельная
нормализованная колонка адреса с индексом. Плюс устойчивость к опечатке в номере
дома и поле `alias` для народных названий крупных объектов.

Хуже: **пустой результат визуально неотличим от «ещё не начал печатать»** —
состояние «0 результатов» в UI не предусмотрено вовсе
(`web/src/app/dispatch/page.tsx:368-396`). Диспетчер с кричащим абонентом не
понимает, думает система или адреса нет.

Отдельно: **во всём остальном приложении поиска по адресу нет** — супервайзеру
на звонок «почему на Тәуелсіздік 33 не закрыты нарушения» найти объект не через
что: на карте 3 `<select>` и ни одного поля ввода.

### 8. Реальное фото с камеры не проходит

Лимит 2 МБ (`web/src/lib/offline.ts:54`), а input открывает камеру напрямую
(`capture="environment"`). Типичное фото телефона — 2–8 МБ. Проверено на 7,4 МБ:
«уменьшите размер перед добавлением», без встроенного сжатия и без подсказки как.
Фото — обязательное доказательство для акта, который идёт в суд.

**Фикс:** сжимать на клиенте через canvas, а не отклонять.

### 9. Закрытие чек-листа стирает отметки молча

Отмечено 2 из 17 пунктов → кнопка «назад» → переоткрыл → 0 из 17. Ни
подтверждения, ни автосохранения. В поле прерывания — норма.

### 10. Донесения защищены хуже визитов

У визитов офлайн-очередь работает по-настоящему (проверена сквозь БД). У
донесений её нет: обрыв связи → сырое `Failed to fetch`, фото не прикрепляется,
отправить нельзя. Инфраструктура (`lib/offline.ts`) уже написана и рядом.

Плюс: **донесение нельзя отправить без фото** (`reports/page.tsx:463`). РТП после
возвращения на базу хочет зафиксировать «планировка 14 этажа не совпала с ПТП,
второй выход был закрыт на ключ» — фотографировать уже нечего, отправить нельзя.
И донесение не привязано к вызову или зданию — следующий караул его на карточке
объекта не увидит.

### 11. Административный акт — одним кликом без подтверждения

Критическое предписание принимается/отклоняется мгновенно, без «вы уверены?» и
без обязательной причины. При этом удаление загруженной карточки (действие
меньшей значимости) защищено `window.confirm`.

### 12. Аудит не отвечает на вопросы комиссии

- Отказы в доступе по GET **не логируются вообще** (5 подтверждённых 403 → ноль
  записей; мидлварь аудирует только мутирующие методы, `api/app/main.py:36-67`).
- Журнал хранит «кто и по какому пути», но не «что»: два `POST /routes/visit` за
  день без `building_id` и статуса. Колонка `detail` заполняется частью роутеров,
  но `audit_log.py:39-50` её никогда не отдаёт.
- Просмотр фото визита (доказательство по протоколу) не логируется, хотя
  просмотр карточки с ПДн — логируется осознанно.
- Каждое «богатое» действие пишется дважды (свой `audit()` + мидлварь).
- Нет пагинации и фильтра по датам: 937 записей за день при лимите 500.

## P2 — доверие, внешний пользователь, мёртвые контролы

### 13. ПДн в карточках замаскированы непоследовательно

В карточке Хайвилл из 14 телефонов замаскирован один. Остальные — городские
шестизначные: приёмная, восемь диспетчерских по блокам, телефоны объекта. Это
служебные номера организации, и караулу они нужны — но **у главного инженера
мобильный закрыт, а у директора ТОО городской рабочий открыт**. Одна категория
лица закрыта наполовину.

Причина: `_mask_contacts` (`api/app/extraction.py:69-79`) работает только в живом
Claude-пайплайне; сидовые карточки идут в БД мимо него — маскировка в них
зашита руками в JSON.

**Требует решения:** где граница между служебным номером организации и рабочим
номером конкретного лица. После решения — прогонять маскирование над сидами при
импорте, а не полагаться на ручную правку JSON.

### 14. Владельцу нечего ответить собранию жильцов

- **«Почему наш дом опасный?»** Бейдж показывает `11` — без подписи, шкалы и
  подсказки. SHAP-объяснение в системе есть, но `GET /buildings/{id}` отдаёт
  владельцу 404 даже по его собственному дому (fail-closed: у owner `district = null`).
- **«Я не согласен с предписанием»** — пути нет ни в UI, ни в API (поиск по
  `dispute|appeal|обжалов|возражени` — пусто). Единственное действие — заявить,
  что устранил, что означает согласие.
- Нет уведомлений о решении: отклонение с комментарием может пролежать неделю.
- `residential` / `other` выводятся сырым английским посреди русского экрана,
  хотя словарь перевода в проекте есть в двух местах.

### 15. Контролы, которые выглядят рабочими, но не работают

- Фильтр «Район» на карте для inspector/supervisor предлагает все 5 районов;
  сервер правильно игнорирует выбор — но пользователь видит «в том районе просто
  нет объектов» вместо «туда нельзя». Отмечено двумя ролями независимо.
- Ссылка «Контроль» на дашборде рендерится всем, но leadership тихо редиректит
  обратно — выглядит как баг, а не как ограничение доступа.
- «LIVE · обновлено HH:MM» — это `new Date()` в момент рендера, а не метка
  свежести данных. Если пересчёт риска сломается на неделю, бейдж всё равно
  покажет текущее время. `/health` с реальной телеметрией существует, но не
  выведен ни на один экран.
- Кнопка «назад» из карточки ПТП сбрасывает РТП в общий список вызовов по
  городу: выбор хранится в состоянии React, а не в URL.

### 16. Нет истории, периодов и экспорта

Ни кнопки экспорта/печати во всём `web/src`, ни динамики неделя-к-неделе, ни
периода в «Контроле выполнения» (только сегодня). Еженедельная сводка
собирается переписыванием чисел в Word руками; на вопрос «а по сравнению с
прошлым месяцем» ответить нечем.

### 17. Подписи расчёта сил у Аланды нечитаемы

Вкладка «Расчёт сил» показывает `A M`, `SП M2`, `NОТД`, `ГТQQ UNITS` — сырые
ключи JSON вместо русских подписей. Словарь `FORCE_FIELDS`
(`web/src/app/cards/page.tsx:1275`) знает только соглашение из `hayvill.json`, а
в `alanda.json` ключи другие и вперемешку кириллица с латиницей. Цифры при этом
верные (4 × 3,7 = 14,8 л/с сошлось с методикой).

### 18. Дыры в демо-данных

- У демо-владельца **ноль предписаний** на обоих его домах — роль owner нечего
  показывать; в городе нет ни одной заявки на устранение, сценарий супервайзера
  «рассмотреть заявку с фото» собрать не из чего.
- У 2256 из 2262 гидрантов пусты `pressure_bar` и `diameter_mm`.
- Активные вызовы копятся неделями (в списке РТП — «сработка сигнализации»
  недельной давности), дубли вызовов на один адрес ничем не различить.

### 19. `import_infra` накапливает дубликаты гидрантов (найдено при уборке)

Скрипт синтезирует гидранты с `osm_id = NULL`, а защита от дублей —
`ON CONFLICT (osm_id) DO NOTHING`, которая для NULL не срабатывает: в уникальном
индексе PostgreSQL NULL ≠ NULL. Каждый прогон добавляет ещё 1128 гидрантов.
База на момент аудита содержала 2262 гидранта — это был результат двух прогонов,
а не эталон; после пересоздания их 1135.

В `preDeploy` на Railway этот скрипт **не входит** (там только alembic +
seed_hayvill + seed_extra_objects), так что прод при деплоях не пухнет — но любой
ручной прогон удваивает сеть гидрантов и портит все метрики по инфраструктуре.

## Что работает — не сломать при правках

Это проверено под нагрузкой реального сценария, а не на глаз:

- **Офлайн-очередь визитов.** Чек-лист заполнен, сеть оборвана, фото приложено
  офлайн, сохранено → синхронизировалось само. Сверено напрямую в БД: код
  нарушения, текст и фото дошли один в один, без дублей.
- **Боевой пакет переживает потерю связи** — полный цикл поллинга в офлайне,
  карточка, гидранты и ссылка на ПТП остались на экране. Именно это нужно в
  подвале и высотке.
- **Пульт ЦОУ проходится с клавиатуры целиком** — Tab доводит до результата
  поиска, Enter выбирает. Для диспетчера это скорость, а не accessibility.
- **Ролевые проверки на уровне API реальны:** ~20 комбинаций роль×эндпоинт, ни
  одной дыры; IDOR и path traversal на портале владельца заблокированы; чужой
  URL редиректит без вспышки контента.
- **Страница «Модель ИИ»** — «проверяя 5% самых рисковых объектов, модель выявляет
  2 из 10 зданий, где случится пожар, — в ×3,9 раза результативнее случайного
  обхода». Единственная формулировка, которую руководство готово произнести на
  коллегии своими словами.
- **Плашки «Демонстрационные данные»** на дашборде, карте и модели — честно и
  заметно.
- **Портал владельца:** один экран, один смысл, мгновенная обратная связь, цикл
  «отклонили с причиной → подать повторно» прозрачен, ни одной пугающей
  необратимой кнопки.
- **Требование фото для нарушения** — правильная защита акта от невнимательности.
- **Маршрут дня действительно приоритизирован** (риск × просрочка, затем порядок
  методом ближайшего соседа), а не отсортирован по алфавиту.
- **Отметка гидранта неисправным** — один тап, кнопка 220×44, мгновенная и
  устойчивая обратная связь.
- **Скорость не проблема:** полный цикл визита — 690 мс системного времени,
  боевой пакет — 625 мс, поиск — 22 мс. Всё остальное время в системе тратит
  человек, а не приложение.
